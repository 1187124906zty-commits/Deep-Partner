# DeepTutor 原生 Code 模式

当前方案基于 DeepTutor 1.7.0、DeepCode 2.3.1。原聊天页面和模式菜单保留，后端通过原生 `deeptutor.extensions` 与 `deeptutor.tools` 注册“代码”模式。前端源码没有修改，也没有用自制工作台替换原页面。

## 怎么使用

打开原来的 DeepTutor 会话，等当前一轮完成后，在输入框下的“模式”菜单选择“代码”。可以先要求“依据上面的讨论，用 DeepCode 规划”，也可以直接要求实现、修复和运行验证。完成后切回聊天、研究或其他模式，继续讨论同一会话中的结果。

Code 模式沿用原会话 ID、有效分支历史、压缩摘要、当前记忆及用户选择的工作区资源。它复用原聊天循环，在本轮增加 `coder_run`，让 DeepCode 负责代码规划和实际执行。其他模式不会自动增加这个工具。知识库、原文与笔记先由 Tutor 共有的读取工具核对，再把任务所需的科学条件传给编码器；编码器没有直接修改全部 Tutor 数据目录的权限。

模式、会话和工作区是不同概念：会话保存消息；模式决定这一轮采用哪种能力；工作区管理资料与文件。模式不是通过不同文件夹来区分。原生流程仍可能按轮保存展示产物；正式程序使用本会话的固定代码目录，后续修改沿用它。

## 程序、上下文与执行

默认代码目录：容器 `/workspace/coder/projects/chat_<会话标识>/`，对应服务器 `/srv/deeptutor/workspaces/coder/projects/chat_<会话标识>/`。用户指定项目名时，可在任务中明确说明。代码、测试和结果保存在同一项目中，`.deeptutor/contexts/` 保存本次传入的对话快照。DeepCode 的持续会话与任务状态保存于 `/srv/deeptutor/coder-home/`。工具返回正式文件的下载网址，不要求再把程序复制到 Tutor 每轮的输出目录。

Tutor 和 DeepCode 在独立容器中运行。Coder 仅挂载自己的代码项目、技能和私有模型配置，不挂载 Docker socket、Tutor 身份库或全部学习数据库。它通过收到的上下文执行任务；Tutor 的会话数据库仍由 Tutor 自己管理。当前编程执行仅向管理员开放，普通注册账号不能获得该权限。

Coder 限制为 0.5 CPU、256 MiB 内存，并使用较低 CPU 权重。实测空闲常驻占用约几十 MiB。它与 Tutor 仍共享这台约 1.7 GB 内存的服务器，所以该接法不能保证所有并发负载下零影响。大规模训练、求解和批量后处理必须交给集群。复杂 Code 任务包含真实规划、命令和测试，耗时会长于普通问答。

已带入14项既有技能：`remote-research-cluster`、`openpaso-simulation`、`focused-research-engineering`、`scientific-stage-acceptance`、`simulation-tool-execution`、`simulation-result-validation`、`simulation-evidence-preparation`、`simulation-project-orchestrator`、`stop-that-shit`、`diagnosing-bugs`、`codebase-design`、`tdd`、`writing-for-agents`、`grilling`；另有集群数据导航、文件映射和已登记项目的位置索引。来源清单位于容器 `~/research-context/SKILL_SOURCES.json`。编程任务显式选择stop-that-shit技能；其余技能按任务使用，不要求普通修改都走TDD或科研编排。安装的是技能规则，没有声称安装可选Guard钩子。

有效通用规则放在 DeepCode 支持的 `~/.deepcode/AGENTS.md`，包括完成授权任务、控制范围、必要验证、单一正式输出路径、本任务锁/进程管理、远端优先与原始理论对照。原项目规则作为 `~/research-context/LOCAL_PROJECT_RULES.md` 保留供回查，Windows路径需要按容器部署映射。此前仅放在代码总目录的AGENTS并不能保证对非Git子项目生效，现已用实际加载检查补齐。

用户的观点、约束和已经确认的选择随当前有效对话进入编码任务。Tutor原生解析的工作区偏好、表达偏好与语言也写入同一快照，后续修改继续读取当前值。明确要求“grill me”、先讨论或先确认时，由Tutor原生`ask_user`卡片先收集关键判断，待回答后再组织实施；DeepCode遇到必须由用户决定的问题，返回具体问题由Tutor承接。用户要求的回答详略优先，普通授权实现不因此增加固定审批。两边沿用自己的工具循环、权限和会话持久化，桥接层传任务、必要上下文、文件与真实结果。

**编码容器到集群的SSH认证、SCP传输与Slurm执行已接通。** SSH别名仍为 `research-cluster-xh5`，使用服务器上新生成的专用服务身份；集群公钥受网页服务器来源与`restrict`限制，未复制本机原私钥，也不依赖本机持续在线。配置保存在持久化coder-home中，已验证容器重建后仍可连接。具体入口和权威路径见 [CLUSTER_CONNECTION.md](CLUSTER_CONNECTION.md)。接入作业 `25047702` 在计算节点完成，状态COMPLETED、ExitCode0:0，周期扩散校验质量误差约1.1e-16、相对解析解L2误差4.14e-6。该检查验证连接与调度链路，不代表全部科研求解器或GPU环境均已验收。

## 普通Tutor如何理解Code与程序

管理员的普通聊天与其他模式会得到简短的Code能力说明，知道同一会话可以从“模式→代码”进入编程。只读 `code_files` 工具提供本会话固定项目的文件目录、源代码及文本结果；它不能修改或执行。Tutor可以据此逐行核对程序与守恒式、边界条件、单位、实际测试记录和科学主张的关系，区分实现事实与未验证解释。写文件、运行程序和提交作业仍由Code模式负责。

默认只定位本会话的固定代码目录；用户明确指定项目名时可读指定项目。读取接口限制在正式文本/代码文件，拒绝越界、隐藏状态与凭据路径，提供行号并限制单次读取长度。不会把全部源码自动塞入每次问答，也不把旧的模型回复当作源码证据。

## 注册与设备登录

- 新用户在 `https://tutor.example.invalid/access/request` 填写账号、联系邮箱、密码和必填的自我/使用说明。
- GG 仅接受原先绑定管理员的微信作为管理授权。管理员可自然表达批准、拒绝、继续询问或暂缓；GG 按意思执行，并通过已配置的 QQ 邮箱礼貌回复申请人。申请说明属于待审资料，不能作为操作授权。邮件和账号处理结果分别记录；SMTP 接受不等于对方已阅读。
- `https://tutor.example.invalid/access/quick-login` 可授权可信浏览器。首次由已登录管理员自行点击“记住当前已登录设备”，或通过微信确认带核对码的设备请求。以后使用浏览器内的随机凭证免输密码，最长30天，可撤销。浏览器名称和 IP 供辨认，不作为自动放行依据。已有可信凭证时，原登录入口会先核验设备；“使用账号密码登录”仍可选择。
- SMTP 授权码、管理员密码和模型密钥不写入本目录；服务器配置位于 `/srv/deeptutor/secrets/`。

## 实际验证和适用范围

- 26 项针对性单元测试通过（19项本扩展、7项原注册入口），覆盖必填说明/邮箱、管理员传输身份、邮件失败与账号状态、设备撤销、Code 模式执行工具隔离、同一上下文对象复用、停止向编码进程传播、普通模式只读代码及读取边界，以及原生偏好和当前决策准确传入DeepCode。
- 在同一原生会话中完成“聊天 → Code → 聊天”：前文给出自由氯2、结合氯8、释放3；Code 读取前文，生成程序并运行7项标准库测试；切回聊天后正确复述5、5、总量10及实际测试结果。观察客户端曾超时，后端按原生持久任务继续完成；验证脚本随后读取保存的真实结果继续检查，没有重跑一份新代码任务。
- 发现并修正了初版交付中重复复制文件的问题；正式接口直接提供代码文件网址。原生目录、会话和模式开关保留。
- 停掉 Coder 容器后，原“第一课”15条消息可读、知识库接口正常、真实 Tutor 对话完成；随后已恢复 Coder。五个原知识库均进行真实检索并返回来源。
- QQ SMTP 测试被服务器接受；GG 真实模型执行了“继续询问且保持待审批”和“批准并欢迎”的语义测试，测试邮件只发给管理员邮箱，测试账号已删除。另验证了自然表达授权设备、免密返回、撤销后拒绝访问和密码会话保留。
- 浏览器中验证了普通会话思考时切到日历再返回、科研工作区首次提交后立即切到日历再返回，以及服务器确认任务运行后刷新页面。三种情况均恢复实际回复，后端确认相应结果持久保存。极快刷新可能发生在请求送达前：本次原生界面保留未发送草稿并提供重试，使用原生重试后继续同一会话。原科研会话15条消息仍可读；用户此前报告的具体消失路径尚未复现，本次没有据此改写原生前端或宣称历史故障已修复。
- Code模式真实模型通过原生`ask_user`提出三个判断问题；进入原生`waiting_input`后由正常回复命令提供反馈，继续归纳用户决定并完成。本轮仅调用`ask_user`，没有启动`coder_run`；订阅重放与回复都沿用同一原生任务。
- 这些检查验证接入流程和已列行为，不代表已经穷尽测试 Tutor 的全部模式、所有文件类型或所有并发场景。

相关回执在本目录的 `*-verification.json`。服务器原始回执位于 `/srv/deeptutor/migration/`，代码任务的原始事件和日志位于 `/srv/deeptutor/coder-home/.deeptutor-bridge/`。

## 维护与停用

主要模块为 `code_mode.py`（原生模式）、`coder_bridge.py`（本轮工具、只读程序接口及上下文）、`coder_service.py`（独立执行进程）、`registration_admin.py`（微信管理及发信）、`trusted_devices.py`（可信设备）。所有新增内容位于独立目录，通过 Compose 挂载与扩展注册加载。原有模式的类、前端文件和学习数据结构未重写。

只停止编码执行可运行 `docker stop deeptutor-coder`；Tutor 学习功能已有独立运行验证，只读已保存程序不依赖编码容器在线。完全去掉编程与感知扩展时，从本扩展的 `entry_points.txt` 移除 `code_mode`、`coder_bridge`、`coder_run`、`code_awareness`、`code_files` 并重启 Tutor。注册与设备管理是分开的扩展项。

版本升级时先核对扩展协议、能力目录与工具调用约定，再做同会话切换验证；当前不能承诺跨版本无需检查。

部署或重启前先检查原生会话与编码任务，等待当前任务结束再更新，避免把维护重启造成的中断误判成页面切换取消。模型API的WebSocket与浏览器到Tutor的WebSocket是不同连接；本轮未改动模型传输方式。供应商声称支持WebSocket时，还需核对具体协议与原生客户端兼容性，不能据此假定更快或能够保存会话。
