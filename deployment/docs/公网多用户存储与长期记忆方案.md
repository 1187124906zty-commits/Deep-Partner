# 公网多用户、集群存储与长期记忆

本方案按用户最新澄清采用 **Tutor 原生个人知识库，账号之间隔离**。不向注册用户开放任意 SQL 服务。本文区分已实施内容、实测结果和正式迁移仍需要的条件。

## 当前判断

公网服务器运行 Tutor、Dify 与工作台，集群承接大文件与计算，这种分工可行。但 SQL、文件、向量索引与会话目前由不同模块保存；仅修改 Dify 的数据库连接不能迁走 Tutor 数据。

本次实际检查：公网磁盘约 59 GiB，已用约 47 GiB，可用约 9.7 GiB。Dify 数据库目录约 86 MiB，工作台 SQLite 约 0.6 MiB；项目输出约 4.6 GiB、解析缓存约 1.1 GiB、账户知识库约 0.9 GiB。容量问题首先在文件与缓存，而不是 SQL。

集群当前连接到 login04，共享存储为 ParaStor；`df` 显示约 159 GiB 可用，标准 `quota -s` 未返回可核对的个人配额。这个数值不能当作已获准用于公网用户的容量预算。默认 PostgreSQL 为 9.2.24，已于 2017 年停止维护（[官方版本支持表](https://www.postgresql.org/support/versioning/)）；本次没有启动数据库常驻进程，也没有把生产数据库搬到登录节点。

推荐先保留小型控制数据库在稳定服务器或专用数据库节点，将用户的大文件通过受认证的存储模块归档到集群。若以后坚持数据库也在集群，需具备稳定常驻节点、受支持的 PostgreSQL、明确的网络入口、可用性承诺及独立恢复副本。不能依赖随机登录节点、短期 Slurm allocation 或个人电脑维持的 SSH 隧道支撑全站登录。

## 数据分别存在哪里

| 数据 | 权威保存方式 | 访问与恢复原则 |
| --- | --- | --- |
| 账户、授权、设备、配额、任务身份 | 小型控制数据库；当前仍沿用原生 JSON/SQLite 与 Dify PostgreSQL | 服务器认证后确定 owner，用户与模型不能自行传入其他 owner；凭据不进入用户文件导出 |
| 会话、项目目录、证据关系、文件版本清单 | 事务元数据与版本化记录 | 对话、任务、来源、产物版本相互引用，保留原 ID |
| 论文 PDF、程序、数据、图表、DOCX/PPTX | 按 owner/project 分区的大文件存储；集群归档层已验证 | 对象不可变；版本切换更新指针；回读验收后才能进入正式迁移切换 |
| 知识库原始资料 | 个人 Tutor KB，默认私有 | 明确授权的共享库单独标识；不能因文件同名或 DOI 相同自动共享个人附件 |
| 解析结果与索引 | 关联原始资料和索引版本 | 活跃索引与检索执行放在同一受控环境；大块不可变索引可归档，不能盲目将活跃 SQLite/索引目录挂到网络盘 |
| 阅读渲染、临时导出、可重建缓存 | 有独立预算与 TTL 的热缓存 | 可以回收缓存，不能用清缓存名义删除原始论文、活动任务输入或用户历史 |

Dify 官方支持通过 `DB_HOST` 等连接数据库，也支持 S3/OpenDAL 文件后端。这是 Dify 自身能力，不等于 Tutor 原生 PathService、个人 KB 与会话已经兼容远程对象存储。[Dify 配置文档](https://docs.dify.ai/en/self-host/deploy/configuration/environments)

SQLite 官方提醒网络文件系统的锁与同步风险，WAL 不能作为多主机访问共享数据库文件的方案。若采用远程数据库，应连接数据库服务器，由其持有数据库文件。[SQLite 网络访问说明](https://sqlite.org/useovernet.html)、[WAL 文档](https://sqlite.org/wal.html)

## 标准用户数据视图

标准化首先规定身份、引用和导出格式，不立即重命名或搬动原生目录。每个文件和索引都有唯一的 owner、项目、逻辑路径、版本和后端位置。

```text
tenants/<opaque-user-id>/
  account.json                 # schema_version、用户资料引用、配额策略版本
  profile/                     # 基础资料和可编辑偏好；不含密码和机构 cookies
  sessions/                    # 原始对话、工具事件、附件引用
  memory/
    trace/                     # L1 原始记录
    L2/                        # 按来源整理的记忆
    L3/                        # 当前范围、偏好、用户资料；可回查 L2/L1
  knowledge/<kb-id>/
    manifest.json              # KB 归属、解析与索引版本
    sources/                   # 原始文献
    parsed/                    # 页码、图表、文本定位
    indexes/                   # 可复现索引快照
  projects/<project-id>/
    project.json               # 问题、任务、原生 workspace、所选技能版本
    src/ configs/ tests/       # 程序、环境、检查
    data/ results/ figures/    # 数据、计算证据、图
    manuscript/ slides/        # 可编辑论文、汇报与导出
    evidence/                  # 具体主张对应的来源与定位
    revisions/                 # 用户版本；仍计入配额
    runs/                      # 运行编号、输入版本、状态、限制与回执
```

这是一份逻辑视图和后续导出约定；原生 Tutor 的 `data/users/<uid>`、workspace catalog 和 Code 物理项目仍保持现有位置。全量物理切换尚未进行。集群归档已使用 `research-tenant-archive/v1` 清单，按 owner_key/project_id 分区，保存 immutable blob 与逻辑路径回执。

## 配额如何更新

已经增加按账号的 `quota_bytes / cache_limit_bytes / archive_quota_bytes / revision` 策略和管理员审计记录。原有工作台固定 2 GiB 限制改为读取当前账号策略；默认额度保持 2 GiB，缓存预算字段默认 512 MiB，归档预算默认 0。降低额度不会删除数据，会阻止超额账户继续新增工作台文件。

当前生效范围是工作台通过 `require_space` 与 `Store.replace` 的项目文件、稿件和历史写入；**不是全系统硬配额**。原生个人 KB 上传、索引增长、Code 输出、会话和缓存的统一事务预留还未全部接入，不能据此开放不限人数注册。归档预算字段也只表示策略，尚未自动给集群分配空间。

已发布接口：

| 方法 | 入口 | 权限与作用 |
| --- | --- | --- |
| GET | `/research/api/storage` | 当前账号用量、当前配额和策略版本 |
| GET | `/research/api/storage/policy` | 当前账号策略与实际执行范围 |
| GET | `/research/api/admin/storage/{owner}` | 管理员读取策略与物理容量 |
| PUT | 同上 | 管理员携 `expected_revision` 更新；普通用户 403，旧版本 409 |
| GET | `/research/api/admin/storage/{owner}/history` | 管理员回查配额变更与原因 |

配额修改通过实际管理接口进行，不需要手工改 SQL。服务器运维命令：

```sh
# 先查账号当前 revision。owner 必须使用真实不可变用户 ID。
sudo python3 /srv/dify-research/ops/storage_quota.py --owner USER_ID

# 示例：将该账号工作台额度调整为 5 GiB，保留 512 MiB 缓存预算。
# 用实际读取到的 revision 替换 0；归档尚未正式分配时保持 0。
sudo python3 /srv/dify-research/ops/storage_quota.py \
  --owner USER_ID --quota-gib 5 --cache-mib 512 --archive-gib 0 \
  --expected-revision 0 --reason '管理员批准该账号工作台扩容'
```

物理存储另有保留线：公网盘默认保留 2 GiB，触线后拒绝新增工作台写入。现有五分钟 Dify 协调任务已同时记录服务器可用空间，无需用模型推理计算配额。

后续全局配额应采用“预留 → 上传/索引/生成 → 按实际增量结算 → 失败释放”的事务。计入原始文件、衍生索引、用户历史与正在上传的暂存；缓存独立设上限。不能每次只扫目录再比较，否则多个进程可同时越额。管理员总承诺额度还要受已核定集群配额和平台保留容量约束，不能给每个注册账号都承诺当前盘上看到的全部空闲空间。

## 长期记忆与流程清晰

Tutor 已有按用户/工作区解析的 L1/L2/L3 记忆，本次沿用，未另加重复的记忆 Agent。用户偏好、项目当前问题和研究证据应分开保存：

- 原始会话和工具事件保存发生过什么；总结帮助续接，但保留来源引用。
- 项目状态记录当前问题、已确认约束、已完成证据、尚待作者判断的内容。
- 结论需要绑定具体来源、页码或运行产物版本；新反证出现时能撤回或修订。
- 用户可查看、纠正和删除自己的记忆；跨项目使用资料需要符合该用户的授权与选择。

迁移后的备份要同时覆盖元数据库、原件、版本清单、索引配置与解密所需的服务器私有配置。集群归档和同一集群上的另一个目录不是独立备份；正式切换前应进行一次异地恢复演练。

## Dify 还要加什么

配额、owner 和路径检查放在存储模块统一执行，Agent、MCP、网页上传和后台任务都必须经过它。不能仅在一张 Dify 图上加 IfElse，就认为其他入口无法超额或越权。

现有成果交付继续承担保存与回读，定时协调已增加磁盘容量状态。后续最有价值的新流程是“资料入库与索引”，建议依次连接：

```mermaid
flowchart LR
    A[用户选择资料与个人知识库] --> B[认证后绑定 owner 和 KB]
    B --> C[存储预留与设备选择]
    C --> D[ScanSci 下载任务或直接上传]
    D --> E{结果状态}
    E -->|需要登录或验证| H[等待对应用户处理]
    H --> D
    E -->|取得文件| F[核对论文身份和文件完整性]
    F --> G[写入用户对象目录并登记版本]
    G --> I[原生 Tutor 索引任务]
    I --> J[回读索引状态与检索来源]
    J --> K[结算配额并返回资料位置]
```

这张入库图为后续实施设计，尚未声称已在 Dify 发布。个人建库、选题、程序、论文、PPT 不应强制串成不可跳过的大图；Tutor 根据任务组合这些有明确输入输出的阶段，关键科学判断回到作者。

## 用户自己的 ScanSci 主机

现有下载队列已经支持本机下载、集群副本验收、用户目录交付。本次补了设备列表、账号隔离和撤销，并把原来的 `owner='*'` 操作员设备限定为管理员自己的任务。普通用户必须配对自己的设备，不能继承管理员机构会话。

| 接口 | 用途 |
| --- | --- |
| POST `/research/api/download-worker/pair` | 当前账号生成下载设备凭据；只显示一次明文 |
| GET `/research/api/download-worker/devices` | 列出当前账号设备，不返回明文凭据 |
| POST `/research/api/download-worker/devices/{id}/revoke` | 撤销当前账号设备；其他账号不能撤销或领取其任务 |

公网用户端应采用主动出站的轻量 worker：用户在自己电脑配对，worker 只领取本账号任务，在本机 ScanSci 专用浏览器完成机构认证，取得文件后凭短期任务凭据上传。服务器从认证身份确定目标 owner/KB，并执行配额、身份核验与索引。用户离线时保留排队状态，人工验证码或登录不能假定已完成。

**现有本机脚本是管理员操作员模式，包含其已有集群 SSH 通路；不能直接当作面向所有用户的安装包。** 公共用户版需由受控上传网关落集群，不向用户分发运营者集群密钥，不开放公网任意本地 MCP 执行入口，也不上传用户浏览器 cookies。本次没有制作或发布公共用户安装包。

另查到当前机器有两个同配置下载进程；已加 OS 级单实例锁并重新启动一个进程树。服务器轮询也不再将仍有心跳的同一任务重复分配给同设备；指定任务恢复和过期恢复分别处理。

## 添加 skill 的方式

可以添加“程序规范”“论文写作”“论文转 PPT”“文献获取”等技能。平台审核过的技能作为可分配版本，用户自定义技能只在自己的命名空间生效，项目清单记录实际使用版本。技能给 Agent 工作方法与产出要求，不能代替账号权限、文件配额或工具授权。

当前 Codex 本机安装的 skill 不会自动出现在公网 Tutor；应通过 Tutor 原生技能资源与工作台的 agent-context 机制接入。程序技能要求实际运行和可复现输入，论文技能要求来源支持和主张范围，PPT 技能要求原文映射、可编辑输出与渲染检查。最终验收由工具和实际产物提供，不能只依据模型说“已符合技能”。

## 本轮已验证与正式切换前的剩余工作

已验证：本地核心及新增测试共 132 项通过；真实两个普通账号创建同名空知识库但目录隔离，跨账号项目读取被拒绝，配额增减立即影响工作台写入，普通用户改配额被拒绝，设备撤销立即生效，测试账号已清理。集群归档另有 10 项真实 SSH 验证，包括重复上传去重、另一个 owner 不能读取、路径穿越、错误摘要、截断传输、超额拒绝和减配额保留文件。

尚未完成的生产切换条件：

1. 核定集群账号可长期用于公网服务的总容量、数据保留与可用性条件；不能把 `df` 当作配额合同。
2. 给原生 KB、索引、Code 输出和会话写入接入统一的事务预算；给普通用户 Code 执行提供实际隔离沙箱。当前审计到的公网 Code 管理接口仍有管理员限制，不能直接开放共享管理员运行环境。
3. 接通活跃文件与索引的远程存储 adapter、缓存回源和源页读取，再迁移。当前归档层不会自动释放服务器空间。
4. 若迁移控制数据库，逐项迁移 Tutor JSON/SQLite 与应用表，保留用户、会话和运行 ID，完成双账号回归和恢复演练；仅修改 Dify 的 DB_HOST 不够。
5. 发布普通用户 ScanSci worker 与受控上传网关，并以两个不同设备和账号验证机构会话、下载、配额、索引与撤销。

用户后续可以先用受控账号和当前存储试跑“个人建库 → 想法讨论 → Code → 论文/PPT”的真实课题，验证使用体验；公网批量注册应等上述存储、配额与执行隔离依赖通过后再启用。
