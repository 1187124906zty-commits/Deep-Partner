# Deep Partner：以连续研究过程组织产品

2026-11-05。依据本次实际页面检查、源码阅读、生产运行记录和用户最新反馈形成。本文是下一阶段实施方案；尚未完成的能力不会写成已交付。当前界面候选未发布，后续界面以本文讨论为准。

## 产品目标

用户已经具备多种工具，核心缺口是这些能力如何在实际研究中连贯使用。Deep Partner 应让用户在同一项目中提出问题、回顾已有认识、寻找证据、编程验证、形成稿件，并能在下一次对话从正确的位置继续。

产品核心是对话记忆、编程、RAG 与文献研究、写作。图形、PPT、知识图谱和工具管理继续保留，但按当前任务需要出现。能力的可见性来自清楚的入口、真实的过程和可继续编辑的成果。首屏不能成为工具卡片目录，工作时也不应同时展示所有功能。

## 参考产品及借鉴范围

1. [Linear：A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh)。官方文章包含界面对照图，强调让当前任务获得主要视觉权重，并减少多余图标和分隔线。借鉴其导航层级、稳定动作位置及克制的视觉分隔。这里采用的是产品界面的原则，不把营销页面搬进工作台。
2. [Notion Enterprise Search](https://www.notion.com/help/enterprise-search)。从问题进入检索，允许指定上下文与来源范围，回答附来源。借鉴“问问题—查看依据—继续工作”的衔接；不要求用户先理解知识库引擎。
3. [Cursor Agent](https://cursor.com/docs/agent/overview)。对话连接读代码、修改、运行和变更回看。借鉴对话与当前文件、执行结果之间的紧密联系，以及执行期间的补充指令。检查点只用于恢复 Agent 修改，长期版本继续交给项目版本机制。

这些参考用于设计取舍，不构成对本项目效果的证明。需要用本项目真实研究任务验证。

## 信息架构与界面方向

### 稳定的页面骨架

左侧为项目及会话导航；中央为当前对话或正在编辑的成果；右侧按需打开原文、引用、代码差异或批注。默认不出现第三栏。用户选中内容或点击来源时，右侧才出现，并保持对话位置、选区、滚动位置和草稿。

项目内保留四个清楚的目的入口：**对话、文献、代码、稿件**。项目切换、搜索、近期会话属于导航；记忆作为项目上下文中的可编辑内容；图表与 PPT 属于成果；知识图谱作为证据关系的一种视图。工具、模型供应商、MCP、Dify 管理等放到设置或执行详情。

新项目的首屏用一句明确说明和四条文字示例表现能力，例如“找出这些论文的方法差异”“基于已有代码实现并验证”“继续上次研究结论”“依据现有证据修改稿件”。这些入口把任务填入同一输入区，不再打开四个互不相干的应用。已有项目优先呈现上次停留处、需要作者处理的一项问题及最近成果。

### 视觉规则

- 主内容使用连续页面，依靠字号、字重、留白、对齐和轻微底色区分层级。
- 有独立操作和边界的对象才需要容器，例如输入框、弹层、差异视图；去掉“标题套框—内容套框—工具条再套框”的重复包裹。
- 首屏只有一个主行动；全局导航退后，当前成果与问题突出。配色在结构确认后选择，浅色与深色分别调校，不继续叠加全局 CSS 补丁。
- 阶段进度默认是一行可展开记录，例如“已核对 8 篇原文，正在比较方法”；等待作者、失败和成果完成清楚可见。
- 动效解释状态变化：来源展开、成果进入侧栏、差异出现、任务完成回执。减少持续旋转、漂浮和无意义入场动画，支持减少动态效果。
- 移动端一次聚焦一个内容面，用返回关系保持上下文，避免把桌面三栏硬塞进小屏幕。

## 四条核心工作流

### 1. 对话与记忆：下次能从正确位置继续

保留现有原生 session/turn 与消息存储，不另起聊天系统。在每轮上下文准备处统一装配：当前请求、当前会话、项目已确认决策、相关证据与成果版本、尚未完成的任务。全文及长日志仍按需读取。

记忆区分当前对话、项目研究状态和个人明确偏好。候选假设不能自动升级为已确认结论，某一课题的参数不能成为全局偏好。每项可持续使用的判断保留来源、适用项目和最近更新；纠正时明确替代关系。用户可以在项目上下文中修正、移除或暂时排除记忆。

默认自动提取和整理，不强迫用户每轮点击“记住”。只有影响科学主线、研究承诺或后续执行含义的决定需要明确确认。界面按需说明本次采用了哪些项目结论。

验证包括长对话压缩、新会话接续、用户纠正旧参数、两个项目同名概念、仅候选的研究想法，以及不再使用已撤回结论。检查实际回答和工具参数，不能只检查数据库中有没有记录。

### 2. RAG 与文献：从检索结果到可核对的论据

建立统一的检索入口和证据返回结构，复用已有语义检索、关键词检索、Scholar、ScanSci 和集群解析。检索前决定本轮范围：当前项目、明确选中文献、关联知识库、外部文献或网页。用户可以覆盖范围；系统不得暗中跨项目取材料。

题录发现、全文取得、解析完成、已读页段、证据综合分别保留状态。上传文件先告诉用户哪些已保存、哪些仍在解析或索引；未就绪的文件不能默默参与全文回答。复用有效解析产物，避免每次查询重新扫描整批 PDF。

回答中的关键主张连接具体段落、页码和源文件版本。点击引用直接打开对应原文，保留左右阅读位置；用户选中文字可继续追问、比较或加入稿件。检索不足、来源冲突与没有取得全文都应直说。先在当前检索链路测基线，再决定是否需要混合召回、重排或查询改写。

首批评测使用本项目约 20–30 个真实问题，覆盖术语、公式、条件限制、跨论文比较和不在库中的问题。记录命中证据、页码正确性、回答支持度、索引新鲜度和耗时，避免凭“搜到一些内容”判定成功。

### 3. 编程：对话能落到当前代码、运行与结果

用户从研究问题或已有代码提出任务。系统明确本轮代码入口、输入材料、运行环境与交付目录，复用原 DeepCode/CLI 执行，持续绑定同一项目、会话和任务。语义规划与代码生成交给执行 Agent，恢复、版本条件、写入和回读由程序约束。

界面把变更文件、运行输出、必要检查和结果文件连到对话。点击文件可阅读或查看差异；用户针对行号、错误或结果继续反馈时，回到同一任务上下文。需要审阅的实施计划显示实际计划与“继续/修改”操作，不让用户去另一个管理控制台寻找待答问题。

完成时分别展示执行状态、测试/数值检查、项目保存状态及尚未满足的条件。失去连接后查同一任务，不再次启动同样的计算。恢复只影响本任务的修改，保留用户并行编辑。

验证以“已有代码修改—实际运行—输出保存—回读—定向再改”完成一个真实闭环，并注入回执丢失、部分保存、版本冲突和长任务断连。

### 4. 写作：围绕当前稿件和证据选择必要步骤

一般对话不再默认启动整条写作流水线。明确写作请求进入写作流程，结合当前稿件、用户选区、研究承诺和可用证据决定做局部修改、章节写作、结构调整或投稿检查。

句段润色只读取必要上下文和依据；章节写作才组织相应段落链；改变全文主线、承诺与兑现关系时提供具体结构建议并取得作者确认。标杆、语料和期刊指南按任务相关性取用，不机械遍历五个角色或每轮全篇打分。

写作基于当前版本生成可检查的差异，保留引文与证据映射。稿件中的作者批注回到原对话，修改后能定位哪些意见已经回应、哪些需要补证据。作者可以接受局部改动；连续多轮编辑保持同一正式稿件。

验证用三类任务：只改指定段落、依据指定文献重写一节、调整全文结构。分别检查范围是否被遵守、证据是否被保留、未授权章节是否被改动、回退及并行编辑是否正常。

## 后端编排的收敛

先建立共同的任务语言，再统一前端展示。每次执行至少关联已有的 project、session/turn、run、source 和 artifact 身份；不要求把现有数据库重写成一个庞大系统。

主对话运行时负责理解与持续互动；原生执行器负责各自任务；Dify 承接已明确的阶段路由和跨服务协调；工作台保存可追溯的材料、版本和回执。对同一事实只保留一个权威状态来源，其他页面读取它。逐步移除两处各自推断完成状态、重复总结、重复发布和重复建任务的路径。

执行事件区分准备、运行、等待服务、等待作者、验证、保存和终态。界面使用研究语言解释，完整技术日志可展开查看。失败告诉用户已经保留什么、缺什么、如何接续，不能只给“重新生成”。

## 实施顺序与每阶段交付

| 阶段 | 核心工作 | 可审阅的结果 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| A. 结构与交互定稿 | 整理上述四条路径、输入框路由、导航与上下文展开方式；确定无重复框的视觉方向 | 对话首页、文献阅读/引用、代码或稿件编辑三个关键界面及状态说明 | 能从界面看懂能力和下一步，且不存在同一任务在模块间重新描述需求的断点 |
| B. 对话与项目连续性 | 统一上下文装配；纠正记忆生效范围；一般对话与写作路由分离 | 同项目跨会话接续及纠错的真实验证 | 能记住正确的内容、更新错误认识、隔离其他项目 |
| C. 文献到论据 | 对齐检索结构、就绪状态、页段证据和引用侧栏 | 真实问题集的基线、改进结果及引用可回读 | 找到可支持回答的原文，空结果和缺口能如实呈现 |
| D. 编程与写作闭环 | 同任务继续、差异审阅、待答操作、版本与回交统一 | 两类实际任务的完整执行和修改记录 | 用户能从结果继续改，恢复不重复执行，保存状态可靠 |
| E. 一体化发布 | 收敛样式与组件；多主题、窄屏、键盘、长内容和异常状态验证 | 候选网页与正式部署回执，必要时同步桌面包 | 真实交互通过后发布，不以静态截图或组件测试代替使用验收 |

实施以完整用户路径为单位，一次打通一条。优先 B/C 的共同上下文与证据基础，同时在 A 中明确视觉骨架，避免分别重做四个漂亮但仍孤立的模块。每阶段只保留与该阶段风险相称的测试。

## 一条贯穿验收的真实使用过程

用户提出一个研究想法；系统带着已有项目认识查文献、核对原文；用户选择一个可验证假设；同一项目生成并运行代码，解释结果；将有证据的结论写入当前稿件；下一次新对话继续处理尚未解决的问题。

贯穿过程检查五件事：用户是否重复解释已经确认的信息，是否被迫复制粘贴跨模块搬运，是否能追到来源和实际结果，是否能对当前成果继续修改，以及中断后是否能接续。功能数量和节点数量不作为成功指标。

## 2026-11-05：工作流管理与规则整理的实施调整

用户补充明确：保留 DeepTutor 内核及新增的 Dify 流程层，检查范围包括编程与写作规则；允许界面和后端一起重构，并希望借助 Linear、Notion 把握全局。以下是这次实现的职责划分，后续改造沿用同一条产品主线。

| 层 | 负责的事实与动作 | 当前处理 |
| --- | --- | --- |
| DeepTutor | 当前对话、来源与原生模型／工具执行 | 继续使用；普通对话默认 research，明确选择写作才在主对话前进入写作工作流 |
| Dify | 已定义的阶段路由与跨服务回执 | 继续使用；保存回执和阶段受理必须核验，不能以 HTTP 节点结束代替实际成功 |
| 项目执行器 | 原任务身份、真实阶段、外部任务编号、暂停和恢复 | 新增持久停留点及暂停请求；恢复复用原 run 与阶段回执 |
| 工作台后端 | 汇总任务、当前成果、评审和规则 | 新增 project_progress 模块，按现有权威状态生成视图，不另造一套状态机 |
| 工作台界面 | 当前工作、需要作者处理的事项、执行详情 | 新增独立工作流页面；复用现有任务详情与控制动作，导航按研究与成果组织 |
| Linear | 本次产品改造的缺陷、任务、里程碑和交付进度 | 待指定团队／项目并接入；尚未创建任何 Linear 项目或问题 |
| Notion | 产品说明、工作流职责、规则依据与决策材料 | 待指定父页面并接入；避免和 Linear 重复维护任务状态 |
